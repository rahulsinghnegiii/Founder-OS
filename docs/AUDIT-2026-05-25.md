# FounderOS Codebase Audit

Date: 2026-05-25

## Executive Summary

FounderOS already has a credible foundation:

- a monorepo split into frontend, API, DB schema, OpenAPI contracts, generated Zod types, and generated React Query hooks
- broad CRUD coverage for core entities
- a working app shell, dashboard, chat surface, workflows, reports, activity log, and revenue views
- a clean enough base to extend incrementally without a rewrite

The main issue is not structural chaos. The main issue is that the current product behaves like a technically competent SaaS dashboard while the target product is an AI-native operational headquarters.

The highest-priority gap is the intelligence layer:

- orchestration is single-agent chat, not multi-agent delegation
- daily briefing is mostly static copy
- reports are template text
- workflows log as successful without executing real steps
- memory exists only as a simple table with no retrieval engine or APIs

The highest-priority UI gap is product identity:

- the current shell is generic dark admin UI
- the reference UI is warmer, more tactile, more department-forward, and more emotionally legible
- the current frontend does not yet expose a true Department Center or visible AI presence

## 1. Architecture Assessment

### What is strong

- Contract-first API setup is a good long-term decision.
  - OpenAPI source: `lib/api-spec/openapi.yaml`
  - Generated Zod/client packages exist in `lib/api-zod` and `lib/api-client-react`
- Data access is centralized in a shared DB package.
  - Schema exports: `lib/db/src/schema/index.ts`
- The repo is already modular across app, server, and shared libraries.
- The frontend uses React Query and route-level pages instead of collapsing everything into one file.
- Activity logging is present and already used by several write operations.
  - Logger helper: `artifacts/api-server/src/lib/activity-logger.ts`

### What is weak

- The API surface area is broader than the actual operational depth.
- Several systems are modeled in schema and routes, but not yet implemented as real engines.
- Frontend information architecture does not reflect the target FounderOS mental model.
- The app shell and visual tokens are generic enough that they obscure product differentiation.

### Architecture conclusion

Do not rewrite the architecture. Keep the monorepo, shared contract setup, and DB-first route organization. The right move is to deepen missing engines behind the existing surface area and to refactor the frontend shell toward a Department Center / HQ model.

## 2. Missing Systems Report

### Missing backend systems

- No memory engine routes or services even though `memories` exists in schema.
  - Table only: `lib/db/src/schema/memories.ts`
  - No memory router is mounted in `artifacts/api-server/src/routes/index.ts`
- No real multi-agent orchestration service.
  - Current orchestrator is one prompt + one model call: `artifacts/api-server/src/routes/orchestrator.ts`
- No model routing, caching, or token governance layer from `masterprompt`.
- No workflow step executor, retry runner, or failure recovery system.
  - Current workflow trigger marks success immediately after `eventBus.emit(...)`: `artifacts/api-server/src/routes/workflows.ts`
- No realtime transport layer beyond client polling.
  - Frontend mostly uses `refetchInterval`, for example notifications and activities
- No auth / authorization / founder-only guardrails.
- No rate limiting, request validation middleware layer, or secure operational audit strategy beyond basic activity rows.
- No vector memory, embedding, semantic retrieval, or memory compression pipeline.
- No proactive intelligence job system for daily briefs, bottleneck detection, or opportunity surfacing.

### Missing data model systems

The `masterprompt` asks for more relational structure than currently exists. Missing or incomplete schema areas include:

- `users`
- `companies`
- `milestones`
- `subscriptions`
- richer entity linking for memories
- workflow approvals
- secure memory access boundaries

Current schema exports stop at 16 core tables: `lib/db/src/schema/index.ts`

### Missing frontend systems

- No dedicated Department Center page in the main app routes.
  - `artifacts/founder-os/src/App.tsx` routes `/agents` but not `/departments`
- No dedicated Notifications page, only a side sheet.
- No immersive Executive HQ page with visible assistant presence, briefing, and operational pulse aligned to the reference screenshots.
- No persistent “living headquarters” activity layer beyond standard cards and lists.
- No founder identity / profile / context system beyond a static `F` avatar.

## 3. Weak Areas Report

### Operational intelligence

- Dashboard briefing is derived from a few counts, then filled with static recommendations and generic summary text.
  - `artifacts/api-server/src/routes/dashboard.ts`
- Reports are templated markdown strings, not synthesized from operational data.
  - `artifacts/api-server/src/routes/reports.ts`

### Orchestration

- Orchestration does not inspect department state, delegate subtasks, or persist structured actions.
- No collaboration graph, no execution planner, no escalation logic, and no output memory update pipeline.
  - `artifacts/api-server/src/routes/orchestrator.ts`

### Workflow execution

- Event bus is only an in-memory `EventEmitter`, so workflow execution is process-local and non-durable.
  - `artifacts/api-server/src/lib/event-bus.ts`
- Trigger route logs success regardless of downstream execution.
  - `artifacts/api-server/src/routes/workflows.ts`

### Frontend IA

- Navigation reflects a generic business app taxonomy instead of the FounderOS HQ model.
  - Current nav: dashboard, chat, projects, tasks, leads, pipeline, agents, workflows, reports, revenue, activities, settings
  - Missing top-level Department Center and Daily Briefing emphasis from the reference

### Data semantics

- Memories are key/value text, which is too weak for a strategic memory engine.
- Activities are untyped enough that downstream reasoning will be noisy.
- Opportunities and revenue are not yet connected into a stronger intelligence model.

## 4. Placeholder Implementation Report

### Confirmed placeholders / thin implementations

- Chat opens with a local hardcoded assistant message and keeps conversation state locally.
  - `artifacts/founder-os/src/pages/chat.tsx`
- Orchestrator fallback response claims systems are fully operational even when AI is not configured.
  - `artifacts/api-server/src/routes/orchestrator.ts`
- Daily briefing summary and recommendations are mostly fixed copy.
  - `artifacts/api-server/src/routes/dashboard.ts`
- Reports are generated from static template functions.
  - `artifacts/api-server/src/routes/reports.ts`
- Workflow trigger marks success without executing defined steps.
  - `artifacts/api-server/src/routes/workflows.ts`
- Department API only returns department rows plus agent counts; no status, activity, health, workload, or agent presence model.
  - `artifacts/api-server/src/routes/departments.ts`
- UI styling tokens are generic dark-mode SaaS defaults with `Inter` and purple-primary accents.
  - `artifacts/founder-os/src/index.css`

## 5. Scalability Concerns

### Backend scalability

- `EventEmitter` workflow orchestration will not scale across multiple instances.
- Orchestrator history query pulls message history directly without summarization or memory distillation.
- No queueing layer for long-running workflows, report generation, or proactive intelligence tasks.
- Notifications and activity feeds lack batching and prioritization strategy.
- Revenue summary and dashboard summary do per-request aggregation rather than materialized summaries or caching.

### Frontend scalability

- Shell is page-centric, but not yet componentized around reusable operational primitives such as:
  - status rail
  - department card
  - AI briefing block
  - operational pulse feed
  - assistant dock
- UI state is still local in places where persisted conversation/session state will be needed.

### Product scalability

- Single-founder assumptions are embedded.
- No permission model.
- No tenant / workspace concept.
- No durable realtime backbone.

## 6. UI/UX Mismatch Analysis

### Reference direction

The screenshots in `UI/` show:

- light, warm, paper-like HQ atmosphere
- thick-outline tactile cards
- strong typographic hierarchy
- department presence as primary information architecture
- clearly visible EA / assistant identity
- constrained playful color system
- minimal but emotionally engaging layouts

### Current mismatch

- Current UI is dark, purple-accented, and visually close to a standard admin template.
  - Theme: `artifacts/founder-os/src/index.css`
- Current sidebar and topbar are generic shell scaffolding.
  - `artifacts/founder-os/src/components/layout.tsx`
- Dashboard is metric-card first, not headquarters first.
  - `artifacts/founder-os/src/pages/dashboard.tsx`
- EA Chat is a standard message panel, not a visible command relationship with the operating system.
  - `artifacts/founder-os/src/pages/chat.tsx`
- Leads page uses a workable kanban layout, but styling still follows generic dark SaaS conventions instead of the reference’s tactile HQ look.
  - `artifacts/founder-os/src/pages/leads.tsx`

### UX implications

- The founder is not getting a sense of “departments awake and on standby.”
- There is not enough emotional reward in opening the app daily.
- The system does not feel proactive enough.
- The assistant is present as a page, not as the HQ layer of the product.

## 7. Orchestration Gaps

- No intent classifier.
- No task planner.
- No department routing logic.
- No multi-agent collaboration state.
- No escalation engine.
- No structured action plan returned from EA chat.
- No background execution queue for delegated work.
- No memory write-back after orchestration steps.

## 8. Memory System Gaps

- No memory APIs despite memory schema presence.
- No short-term vs long-term memory split.
- No entity graph for founder, company, lead, project, or strategy memory.
- No retrieval ranking.
- No summarization / compression.
- No expiry and archive jobs.
- No memory visibility in UI.
- No connection between conversations and memory extraction.
- No pgvector / embedding support despite prompt direction.

## 9. Agent System Gaps

- Agents are currently metadata records, not operational workers.
  - `artifacts/api-server/src/routes/agents.ts`
- No per-agent queue, state machine, work log, or health telemetry.
- No department-specific prompts or capabilities engine.
- No “idle unless needed” runtime policy.
- No “Executive Assistant coordinates everything” mechanism beyond branding text.
- No agent handoff protocol.
- No agent-generated artifacts or structured outputs.

## 10. Operational Intelligence Gaps

- No bottleneck detection engine.
- No forgotten task / opportunity surfacing.
- No lead prioritization engine beyond score display.
- No project risk scoring.
- No workflow health analysis.
- No founder daily brief assembled from cross-domain reasoning.
- No recommendation engine with the requested structure:
  - problem
  - analysis
  - recommended change
  - expected impact
  - risks
  - execution plan

## Prioritized Implementation Roadmap

### Phase 1: Frontend shell and product identity

1. Rebuild the shell around the UI reference:
   - light HQ theme
   - tactile card system
   - stronger typography
   - persistent founder profile block
   - visible EA presence
2. Add dedicated Department Center route and page.
3. Refactor Dashboard into Executive HQ with:
   - live headquarters hero
   - top operational cards
   - daily briefing
   - live activity
   - AI assistant visibility

### Phase 2: Real operational surfaces

4. Upgrade activity feed into typed operational events with priority, department, and action affordances.
5. Upgrade leads into a stronger CRM board with AI cues, follow-up status, and proposal hooks.
6. Upgrade projects/tasks into execution tracking with ownership, blockers, and risk state.

### Phase 3: Intelligence layer

7. Implement memory service:
   - CRUD APIs
   - extraction pipeline from conversations and activities
   - retrieval helpers
   - short-term / long-term separation
8. Implement orchestration service:
   - intent analysis
   - department routing
   - structured action plans
   - memory update after actions
9. Implement agent runtime contract:
   - status transitions
   - work logs
   - task handoff records

### Phase 4: Durable operational systems

10. Replace in-process workflow execution with durable job processing.
11. Add realtime transport for notifications, activity, and AI execution status.
12. Add proactive intelligence jobs for founder briefings, risks, opportunities, and bottlenecks.

### Phase 5: Hardening

13. Add auth, authorization, audit policy, and secure secret boundaries.
14. Add caching, model routing, and cost controls.
15. Add tests for orchestration, workflows, memory retrieval, and realtime behavior.

## Technical Debt List

- UI theme is misaligned with product direction.
- Route/page naming reflects implementation-first taxonomy rather than product-first taxonomy.
- Missing `departments` frontend route despite departments backend support.
- Memory schema exists without service layer.
- Workflow system implies automation but currently lacks execution semantics.
- Reports and briefing are static enough to create trust debt.
- Notification model is too shallow for intelligent alerting.
- No formal domain layer between route handlers and business logic.
- No background jobs / queues.
- No install state in this workspace, so verification is currently blocked.
